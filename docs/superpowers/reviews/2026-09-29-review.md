以下为在等待 Momus 评审结果期间，由我**逐条打开源码实测**确认的问题。均给出 `文件:行号` 或实测输出。

### 🔴 BLOCKER-1：库存/奖池/文案**根本不会被持久化**

**问题**：设计 §7.1 新增了大量 Settings 项（`prize_pool`、`receipt_header`、`receipt_footer`、`shop_name`、`win_title`、`lose_title`、`validity_days`、`printer_*`、`paper_cols`、`logo_*`、`depletion_policy` …），并要求"库存 `remaining` 每次扣减后 `RequestSave()`"（设计 §7.2 / 决策 D12）。

但 `page-player` 的持久化是**两处硬编码字段清单**，新增字段**不会被写入、也不会被读取**：

| 位置 | 事实 |
|---|---|
| `page-player/main/nvs_saver.cc:63-97` | `NvsSaver::DoSave()` 里**逐行硬编码 24 个 key**（`write_i32("working_mode",…)` … `write_i32("dmx_output_mode",…)`）。**不在这个清单里的字段永远不会落盘。** |
| `page-player/main/settings.cc:115-160` | `Settings::Load()` 同样只读**固定 7 个 key**（`nvs_get_i32` + `GetString("timer_start"/"timezone"/"rdm_dev_label")`）。不在清单里的字段重启后**回到默认值**。 |

实测确认：
```
$ grep -c "write_i32\|nvs_set_str" page-player/main/nvs_saver.cc   → 24
$ grep -n "nvs_get_i32\|GetString" page-player/main/settings.cc     → 仅 7 处读取
```

**后果（严重）**：
1. **奖池库存永远不落盘** → 重启后 `remaining` 全部回到初值 → **可以无限次抽中一等奖**（`quantity=1` 形同虚设）。这正是决策 D12 想防的事故，但按现设计**防不住**。
2. 商家在 Web 配的**奖池、文案、引脚、波特率全部丢失** → 每次重启都要重配，现场无法接受。
3. 三级兜底链（NVS → 备份 → 内建）**形同虚设**（前两级都不存在）。

**根因**：`NvsSaver` 是"固定字段批量写"的设计（为了减少 NVS 擦写次数），它**不是通用的 key-value 落地机制**。

**修复（必须，二选一）**：
- **方案 A（推荐，改动小且符合原设计意图）**：把 `DoSave()` 与 `Settings::Load()` 改为**数据驱动**——把字段清单抽成一张 `{key, type, getter/setter}` 表（或让 `Settings` 自持一个 key 列表），四处（声明/getter/setter/序列化）由同一张表驱动，**新增字段只改一处**。这同时消除了"漏加字段"这类未来回归。
- **方案 B（更快）**：在 `DoSave()` 显式补上所有新 key，`Settings::Load()` 补上对应读取。**但必须加一条单测**：遍历 `Settings` 声明支持的全部 key，断言每个 key 都出现在 `DoSave` 的实现里（用静态断言或测试期反射式清单），否则这就是个会反复复发的坑。

**计划侧需要新增任务**：计划 Phase 0 Task 0.3（搬运 Settings/NvsSaver）目前只写"复制 `nvs_saver.*`（原样）"+"复制 `settings.*`，删除非目标项"——**完全没有提到必须扩展持久化字段清单**。这是计划的覆盖缺口（设计也没写）。→ 见下文"计划待补"。

### 🟠 MAJOR-1：设计对"落盘时机"的描述与源码语义不符

**问题**：设计 §7.2 / 决策 D12 写"`remaining` 每次扣减后 `RequestSave()`……若在扣减后、落盘前断电，重启会多出一个库存——有意选择宁多发一个"。

**实际情况**：`NvsSaver::RequestSave()` 是**异步且会静默丢弃**的：

```cpp
// page-player/main/nvs_saver.cc
void NvsSaver::RequestSave() {
    if (queue_ == nullptr) return;
    uint8_t signal = 1;
    xQueueSend(queue_, &signal, 0);   // 非阻塞；队列满（kQueueDepth=2）就丢弃
}
```

- 写盘发生在**低优先级任务**（`tskIDLE_PRIORITY + 1`，`nvs_saver.cc:36`），调用方**不等**；
- 队列深度仅 **2**（`nvs_saver.h:kQueueDepth = 2`），满即丢弃；
- 消费端还会 `xQueueReset()` **主动丢弃重复信号**，只保证"最终有一次写"。

**结论**：设计说的"扣减后立即落盘"**不成立**——实际是"尽快异步写一次，且可能被丢弃"。**但失败方向仍然安全**（NVS 里是旧值 = 库存偏大 = 多发），所以决策 D12 的**结论正确、论证错误**。

**修复**：把 §7.2 的措辞改为准确描述，并明确库存扣减走**同步**路径：
- 库存扣减属低频事件（每次抽奖一次，间隔 ≥5 秒），**完全可以直接 `SaveSync()`**（`nvs_saver.cc:56`，内部同步 `DoSave()`），代价可忽略，且**真正获得 D12 想要的"扣减即落盘"语义**。
- 其余高频字段（如 `current_page`）继续走 `RequestSave()`。
- 文档需写明这个**同步/异步的划分依据**。

### 🟡 MINOR-1：`PageMapping` 默认映射在 30 页时"不退化，但很挤"

**问题**：设计 §5.5 / R13 断言"映射长度不足或行程值退化会导致永远停同一位"，并把 30 页当作高风险。

**实测**（`page-player/main/page_mapping.cc:61-73`，公式 `i * 255 / total_pages`）：

```
N=10 → [0,25,51,76,102,127,153,178,204,229]        distinct=10
N=30 → [0,8,17,25,34,42,51,59,68,76,...]           distinct=30
```

**结论**：默认映射在 N=30 时**产生 30 个互不相同的值**（0~247），**不会退化**。所以"退化"这条断言在**默认映射下不会触发**——它是为"用户自定义映射被写坏"准备的，这个防御仍然值得保留。

**但真正的问题是**：相邻页间隔仅 **8/255 ≈ 3.1%** 行程。翻页机（机械）几乎不可能在这个分辨率下可靠区分 30 个位置，**必须靠 `PageAdjust` 逐页实测标定**。

**修复**：
- 文档应补一句：**30 页的行程值必须实测标定，不能依赖 `SetDefaultMapping()` 的均匀分配**；
- 计划里**缺少"30 页标定/导入"的具体任务**（怎么把 30 个实测值灌进去？`prizes.html` 的"逐页点动"只解决了验证，没解决标定录入）→ 需要补一个任务（见"计划待补"）。

| 11 | `web_server.cc` 被错误的字符串替换写入 79 万行 → 编译 40 分钟 | 工具/流程缺陷 | 重建文件（见下） |

### 流程教训（重要）

修复 #11 的根因：用 `str.index()` 切片 + `str.replace()` 做补丁时，
`old` 取到了**空串或错位片段**，`replace("", new)` 会在**每个字符间插入**内容，
把 596 行的文件膨胀到 **790,727 行**。表现是"编译器卡死 40 分钟"，
实际是 GCC 在畸形源码上做错误恢复。

**对策（已生效）**：
1. 批量编辑源码后必须校验**行数合理性**（`wc -l` 异常即回查）
2. 优先用 `edit` 工具做定点替换，避免 `index()/replace()` 组合
3. 编译"异常缓慢"优先怀疑**源码本身**，而非编译器

> 本次一度误判为"GCC 14 -Og 对嵌套 lambda 的病态实例化"，并加了单文件 `-O1` 绕过——
> 该补丁已撤销（真因不是编译器）。

## 八、更正：打印机引脚回归（2026-09-29 真机发现）

### 事实

| 来源 | 打印机 TX/RX | 判定 |
|---|---|---|
| 设计 §4.3（实物接线图，来自 `tft_displaye/PRINTER.md` 现场实测） | **G9 / G10** | ✅ **正确**（用户 2026-09-29 确认接线为 TX→G9、RX→G10、CTS→G11） |
| 设计 §7.1（Settings 默认值表） | 原写 `43/44` | ❌ 错（43/44 = USB-UART 桥 TX0/RX0） |
| 本次评审 B2 的"修正" | 改成 `47/48` | ❌ **也错**（47/48 是 ESP32-P4 板才只剩的脚；本板是 S3，且 G48 常兼板载 RGB LED） |
| 实现（`config.h` + `static_assert`） | 锁定 `47/48` | ❌ 把错值固化，编译期拦不住 |

### 根因（流程教训）

**把"矛盾的两个章节"统一到了错误的一侧。** B2 发现 §4.3 与 §7.1 冲突：
- §4.3 有**实物证据**（接线照片 + 现场实测"对调后立刻出票"）
- §7.1 只是**配置表**

评审选择了按 §7.1 的语境改（还加了 `static_assert` 强化），于是把正确值覆盖掉了。
**正确做法：矛盾时以"有实物/实测证据"的一侧为权威，另一侧向它对齐。**

### 修复

| 项 | 改动 |
|---|---|
| `config.h` | `PRINTER_TX_PIN=9` / `PRINTER_RX_PIN=10` / `PRINTER_FLOW_PIN=11` |
| 断言 | 由"必须等于 47/48"改为"禁止 43/44、禁止 19/20、TX≠RX"（语义正确：断言防的是已知禁区，不是锁死某个值） |
| Settings | `printer_tx_pin=9` / `printer_rx_pin=10` / 新增 `printer_flow_pin=11` / `printer_flow_mode=0` |
| 文档 | §4.3 补 CTS 接线与方向说明；§7.1 表改 9/10 + 两个流控字段；计划文档引脚块同步 |
| 现场工具 | 新增 `ppins` / `pprobe` / `pswap` / `pflow`（见 §九） |

### 相关：流控方向陷阱（设计文档已记录，此处存档）

G11 的 `CTS` 两个方向含义相反，接反表现均为「一个字节都不打」：
- **RTS 方向**（`pflow rts`）：ESP32 RTS 输出 → 打印机 CTS 输入 = **打印方向**
- **CTS 方向**（`pflow cts`）：打印机 RTS 输出 → ESP32 CTS 输入 = 仅状态回读有意义

默认关闭流控（`printer_flow_mode=0`），避免两个输出端同时驱动一根线。

### 真机验证（2026-09-29）

`pflow cts` 且无打印机驱动 CTS 时：`UART2 发送超时：已发 128/435` → 重试 2 次 → `fail=1`，
**全程无卡死、无看门狗** → 证明设计 M-2「打印机掉线不卡死打印任务」成立。

`ppins` 实测 G9/G10/G11 **三脚均悬空**（电平完全跟随内部上拉/下拉）→
**当时打印机未接在这三个脚上（或未上电）**。
`pprobe` 在悬空脚上曾回读 32 字节**噪声**（`42 08 08 00…` 重复模式）——
**已修正判定逻辑：>4 字节一律判为"疑似线噪"，不再误报"打印机在线"**。

## 九、打印机联调（2026-09-29 完成，用户确认出纸正确）

### 9.1 最终接线（实测确认）

### 9.2 本轮又抓出的 5 个缺陷

### 9.3 可复用的排障方法（本次靠它从错误方向拉回）

遇到**堆损坏/随机崩溃**时，不要靠读代码猜 —— 打开 ESP-IDF 堆投毒，让它在**破坏发生的那一刻**报错并给出真凶回溯：

```ini
CONFIG_HEAP_POISONING_COMPREHENSIVE=y
CONFIG_HEAP_TRACING_STANDALONE=y
```

本次即由它把"TLSF 堆断言"一举定位为"**main 任务栈溢出**"（堆断言只是次生现象）。
定位后应关闭投毒，避免影响真实时序与内存占用。

## 十三、两个真机 Web 问题（2026-09-29，已修）

用户报告：① 手机连上热点后**不自动弹配置页**；② 手动打开 `192.168.4.1/wifi.html` 得到
**"Nothing matches the given URI"**。

### 13.1 问题 ②：所有静态页面 404 —— 漏设通配匹配函数

**根因**：ESP-IDF 的 httpd **默认只做精确匹配**；`/*` 这类通配 URI 必须在配置里显式指定
`config.uri_match_fn = httpd_uri_match_wildcard`，否则 `/*` 被当作**字面量**，永远匹配不上任何真实路径。

**为什么之前没发现**：**HTTP 层从未做过端到端验证** —— 每次都说"要切网络才能测"而推迟。
这次加了**板内自测命令 `httptest [path]`**（设备用 `esp_http_client` 请求自己的
`192.168.4.1`，无需外部网络、无需切 WiFi），一次就把问题钉死：

| 请求 | 修复前 | 修复后 |
|---|---|---|
| `/` | 200 | 200 |
| `/wifi.html` | **404** `Nothing matches the given URI` | **200** |
| `/index.html` | **404** | **200** |
| `/api/wifi` | 200 | 200 |
| `/generate_204`（Android CNA） | **404** | **302 → 配置页** |
| `/hotspot-detect.html`（iOS CNA） | **404** | **302 → 配置页** |

**同时修的坏习惯**：`httpd_register_uri_handler` 的返回值被我全部忽略 →
注册失败**无声无息**。现改为逐条检查并打印失败原因，启动日志明确输出
`路由注册完成：28 条（API 26 + 静态 2）`。

### 13.2 问题 ①：不自动弹配置页 —— 重构时把捕获 DNS 服务弄丢了

**根因**：我把 `wifi_ap.cc` 换成 `wifi_manager.cc` 时，**丢掉了那个监听 53 端口的 UDP DNS 任务**。
DHCP 仍把客户端 DNS 指向 `192.168.4.1`（§11.1 W2 的修复还在），**但没人应答** →
手机 CNA 探测域名解析失败 → 系统认为"这个网络没网"，也就不会弹登录面板。

**修复**：新增 `main/wifi/dns_server.{h,cc}`（学习 page-player `dns_server.cc` 的"就地改造查询包"做法），
并补两处加固：
- 追加应答前做**缓冲区边界检查**（page-player 原实现直接往 512B 缓冲尾部写，理论可越界）
- 每查询日志降为 **DEBUG**（手机一次探测会发多个查询，INFO 会刷屏并拖慢控制台任务）

另：非 A 类型查询（AAAA 等）回「无应答」而不是硬塞 A 记录。

### 13.3 顺带加固：捕获跳转 + 路径穿越防护

- 未知路径一律 **302 → `http://192.168.4.1/`**（比"返回 200 + 首页"更可靠地触发 CNA 弹窗）
- 新增纯函数 `WebPathClean/WebPathIsSafe/WebStaticDecide` 并加**路径穿越防护**：
  `/../settings` 这类请求**绝不落到 `fopen`**（否则可读 SPIFFS 之外的文件），直接走捕获跳转。
  原实现 `"/spiffs" + uri` 拼路径存在穿越风险。

### 13.4 测试与真机确认

- 新增 5 个用例（Web 路径清洗/穿越拒绝/动作判定/已知页面），片上 **195 PASS / 0 FAIL**

## 十五、小票编辑改为画布（可拖动元素）（2026-09-30）

### 15.1 为什么必须动模型，而不是只改前端

原编辑器是**流式块列表**：每个块独占一行，只能设整行对齐。用户要"画布 + 拖动元素"，
最典型的版式（**左店名 + 右日期在同一行**）在原模型下**根本无法表达**。
因此先补模型，再做画布 UI。

### 15.2 模型扩展（向后兼容）

| 字段 | 含义 | 默认 |
|---|---|---|
| `col` | 列偏移（0 = 纸最左）；横向拖动改它 | 0 |
| `row` | 行位置；`-1` = 自动（跟随流式），`≥0` = 钉在绝对行；纵向拖动改它 | -1 |

- **同一 `row`、不同 `col` 的块排在同一行** → 并排布局
- 默认值（`col=0, row=-1`）与旧模板**完全等价**，有回归测试锁定

### 15.3 渲染器重构：两条路径统一内核

排查中发现"预览"与"打印"**各自实现了一套布局**，导致真 bug：

| 缺陷 | 现象 |
|---|---|
| 预览只取折行后的**第一行** | 长文本/多行内容在预览里消失 |
| 二维码预览行**不折行** | 预览行宽 69 列 > 纸宽 32（既有测试直接抓到） |
| feed 行数**重复计算** | 走纸行数不对 |
| 2 倍字号行按整纸宽补空格 | 打印时 32 字符 × 2 = 64 列 → 溢出 |

修法：抽出**唯一的画布排版内核** `BuildCanvas()`（行 → 该行片段），
打印路径与预览路径都消费它 —— **杜绝"两条路径各写一份"这类 bug 之源**。

同时新增两条校验：
- 同一行同一列 → 拒绝（会互相覆盖）
- 同一行混用 1 倍与 2 倍字号 → 拒绝（列坐标量纲不同，必然错位）

### 15.4 编辑器（`receipt.html` 画布版）

- 白纸画布 + 列标尺 + 虚线元素框，`col`/`row` **吸附网格**
- **左右拖动** → 改列位（`col`）
- **上下拖动** → 把元素钉在目标行（`row`）；勾「自动」回到流式
- 点选元素 → 右侧属性（文字/对齐/字号/加粗/分隔字符/二维码参数/走纸/行/列）
- 参数面板点击插入 `{参数}`；「服务端预览」用**真实渲染**（含折行与并排）复核画布
- 打开页面即用浏览器时间给设备校时（AP-only 现场没有 NTP）

## 十六、"无法添加元素"排障（2026-09-30）——前端回归上线

用户报告：打开 `http://192.168.5.72/receipt.html` **无法添加元素**。

### 16.1 三个根因，全是我的错

| # | 根因 | 后果 |
|---|---|---|
| **F1** | `PAPER=$('paper')` **漏了 `#`** —— `querySelector('paper')` 找的是 `<paper>` 标签，返回 null | `paint()` 第一行就抛 `Cannot read properties of null (reading 'style')` → 画布永远空白，点按钮"没反应" |
| **F2** | 画布容器 `id="paper"` 与纸宽下拉框 `id="paper"` **重复 id** | 选择器命中哪个取决于文档顺序，行为不可预测 |
| **F3** | 我上一轮用**正则批量**把 `$('x')` 改成 `$('#x')`，但项目里存在**两种 `$` 约定**：`index/logo/wifi` 是 `getElementById`（调用不带 `#`），`prizes/calibrate/receipt` 是 `querySelector`（带 `#`） | `getElementById('#file')` 全部返回 null → **logo/wifi/index 三个页面报错**；同时 `?? → 三元` 的正则还把 `index.html` 的统计行改成了垃圾代码 `d.if(stats)stats(...)`（**抽奖主页面语法错误**） |

> F3 是**同一个坑第二次踩**（本项目此前有过 `#std` 正则改坏源码、`console_cmd.cc` 批量插入失败）。
> 这次之所以能当场收敛，是因为**跑了真实浏览器**，而不是"看代码觉得没问题"。

### 16.2 修法

1. **`$` 统一为一个兼容两种写法的实现**，从根上消除该类错误：
   ```js
   const $=s=>document.querySelector((s[0]==='#'||s[0]==='.')?s:('#'+s));
   ```
2. 画布容器改名 `#canvas`，消除重复 id；补全所有漏 `#` 的选择器
3. `index.html` 统计行改回显式判空写法
4. **静态响应加 `Cache-Control: no-store`**：此前**没有任何缓存头**，浏览器启发式缓存会让用户一直看到旧页面（"改了没生效"的常见误判来源）
5. **页面自诊断**：`window.onerror` / `unhandledrejection` 把错误显示成顶部红条
   —— 现场排障不必再连电脑看控制台，用户可直接转述错误信息

### 16.3 新增自动化守卫：`scripts/web_smoke.py`

后端单测（213 例）与 HTTP 验收（50 项）**都覆盖不到前端 JS**，这正是 F1–F3 能漏出去的原因。
新增真实浏览器冒烟脚本（playwright）：

```bash
python3 scripts/web_smoke.py 192.168.5.72
```

- 6 个页面逐个加载 → 断言无 JS 异常、无错误提示条
- 画布交互：新增元素 / 属性改文字 / **横向拖动改列** / **纵向拖动钉行**（并断言不累加跑飞）/ 服务端预览 / 保存 / 清理复原

**结果：15 通过 / 0 失败**。

### 16.4 顺带修掉的真实缺陷

**纵向拖动会"加速跑飞"**：拖动基准行每帧重算（`layout()` 随着 `row` 被改写而变化），
下拖 2 行实际会跑到 +6 行以上。修法：基准行在 `pointerdown` 时**一次性固定**，
并加断言 `row == base + 1` 锁死该行为。

## 十七、编辑模板时报 "chrome: call method timed out"（2026-09-30）

### 17.1 复现与根因：**每敲一键发一次预览请求**

用真实浏览器打字实测：**输入 15 个字符 → 16 次 `POST /api/receipt/template/preview`**。
编辑器把预览绑定在 `oninput` 上且无节流，等于把 ESP32 的 HTTP 服务当成本地服务打。

- 设备端 `httpd` 默认 `max_open_sockets = 7`，连接一堆积就直接失败
- 前端 `fetch` 失败 → 触发我上一轮加的 `unhandledrejection` 错误条
- 用户看到的就是那条 `Window message "chrome: call method" timed out.`
  （该文本来自浏览器/扩展层，但**触发条件是我们自己造成的请求风暴**）

### 17.2 修法

| 层 | 措施 |
|---|---|
| 前端 | **防抖 350ms** + **单飞（同一时刻只允许一个在飞）** + **`AbortController` 取消旧请求** + **按序号丢弃过期响应** |
| 前端 | 网络类抖动（abort/timeout/Failed to fetch）**不再弹错误条**；真正的失败提示为可操作文案「预览刷新失败（点「刷新预览」重试）」 |
| 前端 | 错误条**同类错误只提示一次**，避免刷屏 |
| 设备端 | `max_open_sockets 7 → 12`、`backlog_conn = 12`、`lru_purge_enable = true`（连接满时回收最久未用的，而不是拒绝新连接） |

### 17.3 实测效果

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 连续输入 15 个字符 | **16 次请求** | **1 次请求** |
| 连点 8 次「＋ 分隔线」 | 8 次 | 8 次（每次点击本就该刷新一次） |
| 错误条 | 频繁弹出 | 空 |

回归：`web_smoke.py` **15/0**、`api_verify.py` **47/0**。

### 17.4 又一次"改了没生效"的教训

第一版修补丁时，`setF()` 改成了 `render(350)`，但 **`render()` 函数体的替换字符串没匹配上**
（Python `str.replace` 静默不做任何事）→ 防抖形同无物，实测仍是 16 次请求。

**教训**：批量/大段文本替换后**必须用 grep 或实测复核**，不能只看"脚本没报错"。
这次的复核方式就是重新数请求次数 —— 数字从 16 变 1 才算真的改上了。
（本项目同类问题已出现多次，故 `scripts/web_smoke.py` 已把"输入后请求数"列为可回归项。）

## 十九、"二维码/Logo 当背景、文字叠加"（2026-09-30）—— 现场结论：本机不支持

### 19.1 需求与技术约束

用户希望把二维码或 logo 当背景、文字叠在上面。热敏机是**行式打印**：
图片按"点阵带"整体输出，机器随后走纸 —— 图片与文字处在**不同的纸面行**上。

要让文字**真正压在图上**，唯一途径是 **ESC/POS 页面模式**：
`ESC L`（进页面模式）→ `ESC W`（设定页面区）→ `ESC $` / `GS $`（按点定位）→
`ESC FF`（整页输出）→ `ESC S`（回标准模式），重叠处的点由打印机做"或"。

### 19.2 实现并现场实测

已完整实现（可测的纯字节序列）：

- 模型新增 `bg` 字段（仅 **logo** 允许；二维码禁止 —— 见 19.3）
- 渲染器新增 `RenderPageMode()`：背景层先按坐标铺图，前景文字再按坐标叠加
- 新增串口命令 `pbg [on|off]`：打"背景叠加样张"并切换页面模式开关
- 设置项 `pagemode`（默认**关**，键名 8 字符满足 NVS ≤14 限制）
- 单测 5 例：背景允许重叠 / 仅 logo 可为背景 / JSON 往返 /
  页模式仅在开关打开时启用且指令齐全（`ESC L` `ESC W` `ESC FF` `ESC S` `GS $`）/
  无背景元素时**不得**走页模式（保护既有版式）

**实测（真机出纸两张：行式对照 + 页模式叠加）**：
指令确认已正确发出（`1B 4C` / `1B 57 00 00 00 00 80 01 F0 00` 页面区 384×496 点 /
`1B 24 60 00` / `1D 24 18 00`），但**纸面效果与行式完全一样** ——
即该打印机**忽略页面模式指令**，仍按标准模式逐行输出。

> 现场结论（已写进 `pbg` 命令的输出，避免后人重复试错）：
> **本机不支持页面模式，真正的"文字压图"做不到。**
> 页面模式代码保留（有测试），换支持该指令的机型即可直接复用。

### 19.3 按用户选择确定的最终策略

用户确认：**"logo 当水印可叠加，二维码不做背景"**。据此落地：

| 项 | 策略 |
|---|---|
| 二维码做背景 | **禁止**（校验直接拒绝，提示"会遮挡码点、影响扫码"） |
| logo 做背景 | 允许勾选「作为背景水印」；该块**不占流式行**，便于把文字排在它前后 |
| 画布提示 | 明确写出：本机不支持页面模式，图片占满自己那几行，文字只能在**上方或下方** |
| 页面模式默认 | **关闭**（官方默认），不影响任何既有版式 |

### 19.4 顺带修掉的两个自身问题

- **NVS 键超长**：`printer_pagemode` 是 **16 字符**，超过 NVS 上限 14（我一开始还误报"✓"）
  → 改名 `pagemode`。幸好有 `Smoke.AllNvsKeysFitLimit` 单测与编译期类型检查兜底。
- **结构体字段插队**：`bg` 插在 `row` 之前，破坏了代码里大量**位置初始化**
  （`{type, text, align, ...}`）→ 编译报 narrowing。改为把 `bg` 放到结构体**末尾**，
  保持既有初始化兼容。

测试：片上 **219 PASS / 0 FAIL**，前端冒烟 **17 / 0**。

## 二十一、绘图模式（图形模式）实现 —— 文字真正压在图上（2026-09-30）

用户问"能否采用绘图模式"。**能，而且这才是本机唯一可行的叠加方案**：
不再依赖打印机的页面模式，而是**把整张小票在设备端合成成一张点阵图**，
再用 `GS v 0` 整幅输出 —— 文字与图是同一张位图上的像素，**天然可任意叠加**。

### 21.1 代价与做法：设备端需要点阵字库

要让设备"把文字画成像素"，必须有字形点阵。做法：

| 项 | 说明 |
|---|---|
| 字形尺寸 | 与打印机 FONT A **对齐**（ASCII 12×24、汉字 24×24）→ 图形模式与文字模式**行宽完全一致**，版式不变 |
| 字库来源 | `tools/gen_font.py`（Mac 上用 PIL 从系统字体生成） |
| 覆盖率 | **完整 GB2312**：7542 字形（7447 汉字 + 95 ASCII） |
| 体积 | 616.5 KB（app 1.91 MB / 3 MB 分区，余 39%） |
| 存放 | `EMBED_FILES` **嵌进固件**（不放 SPIFFS —— 烧固件/OTA 会重写 SPIFFS，用户素材会丢，见 G3） |
| 格式 | `F24A` + count + 索引（Unicode + 宽高 + 偏移）+ 逐行 MSB 点阵；设备端**二分查找** |

### 21.2 渲染决策链（有背景水印块时）

```
① 页面模式（打印机自己叠加）  ← 本机实测不支持（评审 §19）
② 图形模式（我们自己合成位图） ← 本机走这条
③ 文字模式（图与字上下分层）  ← 字库缺字时自动回退，并按字符告警
```

**关键安全设计**：图形模式前先检查**全篇字形是否齐备**；缺字则**整张退回文字模式**并打印
缺失字符（例：`字库缺少 3 个字符「水」→ 本张退回文字模式`）—— 绝不打出乱码或缺字小票。

### 21.3 本轮修掉的三个真问题

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| **G4** | 设备**无限重启**（46 次 abort） | 上一轮烧过测试宿主（分区表无 `assets`），随后 `appflash` **只烧 app 没换回分区表** → 主固件 `esp_vfs_spiffs_register` 失败 → **`ESP_ERROR_CHECK` 直接 abort** | ① 缺 SPIFFS 改为**降级不 abort**（Web 素材不可用，但抽奖/打印继续 —— 同"网络失败不变砖"原则）② `appflash` 改为 **app + 分区表**一起烧 |
| **G5** | 字库缺常用字（稳/敌/杂/艳…） | **PingFang.ttc 在 22px 下把部分字形渲染为空白**（0 黑点），而生成脚本只试了一个字体 | 字体优先级改为 STHeiti 优先 + **逐字体回退**；缺字从 26 个降到 4 个（仅 `│┆┊` 等装饰符） |
| **G6** | 常用字缺字形会静默打错 | — | 生成脚本把"渲染为空白"的字形**列出来**，运行时再做齐备性检查与回退 |

### 21.4 实测

```
BmpCanvas: 点阵字库就绪：7542 个字形，631256 字节
ReceiptRender: 图形模式合成完成（15085 字节）
PrinterSvc: 整帧 15085 字节（logo 已包含）
```

## 二十三、乱码真凶：`raw_printer_raw_write` 的**硬编码 1000ms 超时**（2026-09-30）

### 23.1 真凶不在缓冲、不在流控，而在超时

```c
printer_status_t raw_printer_raw_write(raw_printer_t *printer,
                                       const uint8_t *data, uint16_t size) {
    return append(printer, data, size, 1000);      // ← 硬编码 1000ms
}
```

- 我们的暂存缓冲只有 512B（对齐参考实现），帧超过它时走 `send_direct(..., 1000)`
- 115200 baud ≈ 11.5 字节/ms → **15KB 帧纯传输就要约 1.3 秒**
- ⇒ 1000ms 超时**在半途掐断发送** → 打印机收到残缺字节流 → **解析错位 → 整张小票乱码**

**证据链完全吻合**：493B（0.04s）✅、5746B（0.5s）✅、15085B（1.3s）❌。
我先前归因于"打印机输入缓冲被冲爆"并去开 CTS / 加限速，**方向错了** ——
限速反而把超时窗口内的耗时拉得更长，故障依旧。

### 23.2 两处修正

| 修正 | 内容 |
|---|---|
| 发送接口 | 改用 `raw_printer_raw_send(prn, data, size, timeout)`，超时**按帧大小计算**：`500 + size*3/11` ms（3 倍余量 + 固定开销） |
| 撤回误判补丁 | 撤掉"每 1KB 限速 12ms"的分块节流（真凶是超时，限速无益且拉长耗时） |

### 23.3 顺带落地：混合模式（本轮主要目标）

**只有与背景图重叠的行**走位图，其余仍走打印机文字：

```
混合模式合成完成（5949 字节，仅重叠行走位图）    ← 原整幅位图 15085 字节
整帧 5949 字节（logo 已包含）
打印完成 (ok=1 fail=0)                        ← 一次成功
```

- 关键细节：混合模式必须显式设 **`ESC 3 24`（行距 = 24 点）**，否则打印机默认行距（约 30 点）
  会让位图带与前后文字行**错位**；结束时用 `ESC 2` 恢复默认
- 附带好处：**字形覆盖只需覆盖重叠区**（不再要求全篇齐备），而且帧小、打印快

### 23.4 测试与现状

- 片上 **228 PASS / 0 FAIL**
- 设备：主固件（整包）+ 水印叠加演示版式 + 水印图已上传，打印正常（`ok=1 fail=0`）
- 版式存 NVS，**烧固件不会丢**；水印图存 SPIFFS，**整包烧录会丢**（改用 `appflash` 可保留）

### 23.5 教训（本轮第二次同类）

**"排障工具的自身缺陷会伪装成产品缺陷"**（前有 `pdump` 只留尾部 1024B，今有硬编码超时）。
两次都是**用一个独立证据**（整帧字节数 / 帧大小与超时的量纲对比）才纠正过来。
归因前先做**量纲估算**（本例：15KB ÷ 11.5 B/ms = 1.3s > 1.0s 超时）能避免整轮白跑。

## 二十五、大帧乱码的真正完整解法：**充足超时 + 主动限速 + CTS**（2026-09-30）

### 25.1 现象递进

| 帧大小 | 结果 | 说明 |
|---|---|---|
| 493 B / 5746 B / 5949 B | ✅ 正常 | 远小于任何瓶颈 |
| 15085 B（修超时前） | ❌ 乱码 | 被 `append(..., 1000)` 硬编码超时**半途掐断** |
| 11678 B（修超时后） | ✅ 正常 | 超时修复生效 |
| 23279 B（仅修超时） | ❌ 乱码，但 `ok=1` | **写入成功、打印机来不及消费 → 输入缓冲丢字节** |

**结论：这是两个独立瓶颈，必须同时治**

1. **发送方超时**（1000ms 硬编码）→ 用按帧大小计算的超时解决
2. **接收方消费速度**（热敏机烧点速度跟不上 UART 的 ~11.5 字节/ms，
   密集位图更慢）→ 用**主动限速**（每 512B 等 FIFO 排空 + 停 18ms ≈ 8 字节/ms）
   并**打开 CTS 硬件流控**（打印机可用 CTS 主动喊停）

> 教训：我先前"撤回限速"是**过度纠正** —— 当时限速无效是因为真正的瓶颈（超时）
> 没解决；两个瓶颈并存时，只解一个仍然失败，容易误判为"这个手段没用"。

### 25.2 同时开启后的实测

```
流控=1（CTS，脚 G11）
混合模式合成完成（23279 字节，仅重叠行走位图）
整帧 23279 字节（logo 已包含）
打印完成 (ok=1 fail=0)
耗时：约 5.9 秒（限速 + CTS 暂停共同作用，说明打印机确实在"喊停"）
```

**代价**：大帧打印变慢（23KB ≈ 6 秒/张）。这是"位图背景"方案的固有成本，
可用"缩小背景图高度 / 减少重叠行数"来换取速度。

## 二十七、"二维码与边框间隔太大"（2026-09-30）

### 27.1 根因：混合模式把二维码放到**最后**打印

`RenderHybrid` 的行循环先输出所有内容行（含二维码所在的空行、以及模板末尾的 `feed` 空行），
**最后**才统一打印二维码 —— 于是二维码与边框之间凭空多出：
`二维码行之前 + 二维码自身行 + feed 4 行` ≈ **7 个空行（约 21mm）**。

### 27.2 修法

| 项 | 修改 |
|---|---|
| 二维码 | **就地打印**（走到它那一行就发指令），并按 `ceil(29 × 模块尺寸 / 24)` 跳过它实际占用的行，不再多留空行 |
| feed 空行 | 从行循环里摘出，**统一放到最后**（必须在二维码之后，否则裁剪空行会跑到码上面） |

### 27.3 与模板配合

二维码 `row=28` —— 正好紧贴 28 行高（672 点）的边框图带，实现"边框一出、紧接着就是码"。

实测：
```
混合模式合成完成（32555 字节，仅重叠行走位图）
打印完成 (ok=1 fail=0)
```

### 27.4 顺带说明

**纯文字模式**不存在此问题：块按行序输出，二维码本就在其行位置发出、feed 也在其后。
该缺陷是混合模式引入的（为处理"二维码不参与叠加"而把它挪到了末尾），
属回归，已由"就地打印"纠正。

| **banner** | 9 | 上下花边 2/3 行 + 中间文字 + 二维码 + 4 空行 | ~6.4 KB / ~0.9 s |

- 写各槽时 `PUT` 会把该模式设为生效，故均**写完即还原**为用户在用的 banner 模式

- canvas 标准版式替换了原先的内置水印版式（后者只有 9 行内容，配 28 行边框会下半空置）

**用户可用**：画布页「版式类型」下拉切换 → 载入该类型模板 → 编辑 → 保存。

## 三十一、"打测试页打的不是当前模板"（2026-09-30）

### 现象与根因

用户在画布页选了某类型（或改了版式）后点「打测试页」，打出来的是**上次保存的**模板。

根因：`POST /api/printer/test` 走 `Application::PrintTestTicket()` →
`printer_service_->Enqueue(LoadTemplateFromSettings(), ...)` —— 打的是**设备上生效模式的已保存模板**。
而 UI 里切换类型只是**载入到画布编辑**、改动也只在浏览器内存里，都**没有保存**，
所以测试页反映的必然是上一次保存的内容。

### 修法：所见即所打

| 层 | 变更 |
|---|---|
| 接口 | `POST /api/printer/test` **带模板 body 时打印 body 里的模板**；不带 body 才打已保存的（返回 `source: editor/saved` 便于区分） |
| Application | `PrintTemplateForTest()` 改为返回是否入队成功（忙时接口回 503，前端能提示） |
| 前端 | 「打测试页」把**当前画布内容**（`payload()`）一起发出，并提示"已按当前画布内容（N 个元素）发出测试页" |

### 验证

```
选 canvas 类型（设备生效模式是 banner）→ 点「打测试页」
前端提示：已按当前画布内容（18 个元素）发出测试页
打印机：  ok=1 fail=0
```

即**未保存的改动也会照当前画布打印**，符合"测试页"的预期语义。

## 三十二、"打印布局过错"：背景层标记被编辑器保存时丢掉（2026-09-30）

### 现象

纸面：**边框整条打在票头（空的），所有文字排在框下面** —— 即"画布版式被按纯文字模式渲染"。

### 根因（一个字段）

```
canvas 槽实际内容: mode=canvas 块=18 bg=0     ← 背景标记没了
```

编辑器的 `payload()` **没有回传 `bg` 字段**：

```js
const o={type:b.type}; if(b.col) o.col=b.col; if(b.row>=0) o.row=b.row;
if(b.type==='line'){...} ...          // ← 全程没有 bg
```

后果链条：**在画布上点一次「保存模板」→ 背景层标记丢失** → 模板退化成
"canvas 模式 + 普通图片块" → `HasBackground()` 为假 → 渲染落到**文字模式** →
图片作为独立图带先打（占 28 行），文字按行坐标跟在后面 → 正是纸面现象。

**是我自己的冒烟测试点过「保存模板」把它弄丢的**（此前所有 canvas 打印都正常，
只有经过编辑器保存后才坏）。

### 修法

| 层 | 变更 |
|---|---|
| 编辑器 | `payload()` 回传 `bg`（含注释说明后果） |
| 冒烟测试 | 新增两条断言：**画布模式载入后有背景元素**、**保存后背景层标记未丢失**（锁死该回归） |
| 冒烟测试 | 拖动前 `scroll_into_view_if_needed()` —— 画布模式内容长，元素落在视口外时鼠标点不到（原两条拖动失败的真正原因是测试没滚动，不是功能坏了） |
| 数据 | 重装 canvas 槽（含背景层）→ 实测 `混合模式合成完成（32559 字节）`、`ok=1` |

### 验证

```
web_smoke：19 通过 / 0 失败（含新增的背景层两条断言）
画布模式出票：混合模式合成完成（32559 字节，仅重叠行走位图）→ ok=1
```

### 教训

**"编辑器保存 → 后端渲染异常"这类问题的第一步，是比对"存的"与"渲染读的"字段集合。**
本次只用一条命令就定位（读回模板数 `bg` 个数 = 0）。
今后新增任何块字段，**必须同时检查三处**：`ToJson`/`FromJson`、编辑器 `fromServer` 与 `payload`。

## 三十三、缺纸探测上线 + 换纸复验（2026-09-30）

### 33.1 需求与实现

用户要求"出票前自动探测纸尽"。实现：

| 位置 | 行为 |
|---|---|
| 出票前 | 发 `GS r 1` 查纸传感器；纸尽 → **跳过本张** + `E` 级告警 + 计数（抽奖主流程不受影响） |
| 出票后 | 复探一次，捕捉"打到一半纸用尽" → 提示"本张可能不完整，请换纸后重打" |
| 容错 | **无应答按"有纸"处理**（部分廉价机型不支持该指令，不得因此阻断出票） |
| 接口 | `/api/status` 增 `printer_paper_ok` / `printer_skipped`；串口 `pstatus` 显示 `纸=/缺纸跳过=N` |
| 代价 | 每张票 +约 0.4 秒（两次短往返） |

纯函数 `PrinterPaperEndFromStatus()`（bit2..3 == 11 = 纸尽）有单测，断言用**真机实测字节**（0x00 有纸 / 0x0F 纸尽）。

### 33.2 真机验证（恰好赶上真缺纸）

```

        PRINTER 纸=⚠ 缺纸  缺纸跳过=3 张
        接口: printer_paper_ok=False  printer_skipped=3
换纸后：GS r 1 = 0x00 → 有纸；打印成功 ok=2，纸=有纸
```

**没有浪费纸、没有打出半张空票** ✓ 这正是该功能要解决的场景
（此前 32KB 边框票打到一半没纸，系统全程显示 ok=1）。

重传后恢复正常（`32559 字节 / logo 已包含`）。**已在 §20.2 G3 记录**；

## 三十四、用户素材独立分区 + 三版式出厂预设（2026-09-30）

用户要求做两件事，均已完成并真机验证。

### 34.1 素材（logo/边框图）迁到独立分区

**问题**：素材原存 `assets`(SPIFFS)。该分区是**构建期生成**的镜像，每次
`idf.py flash` 都整块重写 → **上传的图被冲掉**（真机反复踩坑，评审 G3）。

**方案**：新增 raw flash 分区 `logo`（`data,0x40,0xD00000,0x20000`），
`LogoStore` 重写为直接用 `esp_partition` 读写：

| 项 | 实现 |
|---|---|
| 格式 | `LOGO` + len(u32) + **CRC32**(u32) + LGO1 数据 |
| 写入 | 按 4KB 对齐擦除 → 写头和体 → **回读校验**（写坏当场发现） |
| 容错 | 任一步失败保留旧数据（D15）；CRC 不过视为无效 |
| 迁移 | 启动时 `MigrateFromSpiffsIfNeeded()`：新分区为空且旧 SPIFFS 有图 → 一次性搬迁 |

**真机验证（关键）**：
```
烧录前: {"exists":true,"width":384,"height":672,"bytes":32264}
整包烧录（重写 SPIFFS assets）
烧录后: {"exists":true,"width":384,"height":672,"bytes":32264}   ← 素材存活 ✅
```

### 34.2 本轮踩到的坑：48KB 栈缓冲把设备拖死

新 `LogoStore` 第一版在 `ReadValidLength()` 里用了 **48KB 的栈上数组**
（`kMaxLogoBytes` 已抬到 48392）→ HTTP 任务栈仅几 KB → **栈溢出**，
USB 外设被一起拖死（**串口都不出字**，一度以为设备变砖）。

修法：所有 48KB 级缓冲统一走 **PSRAM 暂存**（`Scratch()`，一次分配）。
> 教训：**大缓冲永远不许放栈上**；`kMaxLogoBytes` 这类"配置常量"随需求变大后，
> 原本安全的栈数组会突然变成炸弹。

### 34.3 三种版式的出厂预设 + 一键全部重置

| 模式 | 出厂预设 | 块数 |
|---|---|---|
| flow | 经典纯文字（店名/标题/奖项/票号·时间·页码·校验/提示·有效期/二维码/4 空行） | 15 |
| canvas | 边框叠加（背景层 + 内容铺满 28 行 + 二维码 + 4 空行） | 18（**bg=1**） |
| banner | 上下花边 2/3 行 + 中间文字 | 9 |

- 新增接口 **`POST /api/receipt/template/reset`**：`{"mode":0|1|2}` 重置单个、
  `{"mode":-1}` 或空 body = **三种全部重置**（并把生效模式置回 flow）
- 画布页新增按钮「**全部重置为出厂**」（原有「恢复出厂」改名"当前类型"）
- 单测：`Presets.PresetsAreValidForAllModes`（1..6 全预设合法 + 三模式预设模式正确 +
  canvas 预设必须带背景层）、`Presets.ResetAllWritesAllThreeSlots`
