# 评审：GPIO 恢复默认配置按钮（长按 5 秒）

> 设计 `specs/2026-10-10-reset-button.md`　|　计划 `plans/2026-10-10-reset-button.md`
> 需求："GPIO4 作为恢复默认配置按钮，默认上拉高电平、按下低电平、长按 5 秒触发恢复默认配置，
> WiFi AP 密码恢复为 12345678"

## 1. 引脚：G4 冲突 → 换到 GPIO5（已与用户确认）

**GPIO4 已经是 DMX512 的 DE（发送使能）输出脚**（`DMX512_DE_PIN`，初始化即拉高），
改作按钮会破坏 DMX 输出。用户选择"按钮换到其它空闲脚" → 选 **GPIO5**：
非 strapping、无板上外设、无 USB/Flash/PSRAM 复用；并加**编译期断言**锁死它不得与
抽奖键(8)/红外(3)/打印机(9,10,11)/DMX(17,18,**4**)/USB(19,20)/UART 桥(43,44) 任一冲突。

## 2. 恢复范围：仅网络配置（已与用户确认）

| 复位 | **绝不动** |
|---|---|
| `ap_ssid`→默认名、`ap_pass`→**12345678**、`ip_mode`→DHCP、`st_ip/mask/gw`→空、`wifi_ssid/wifi_pass/wifi_list`→空 | 奖池、三种小票模板、标定偏移与基础映射、累计开奖数、票号、店铺名、打印机参数 |

`Settings::ResetNetworkConfig()` 只改那 9 个字段；**单测用哨兵值锁死"数据字段一字不变"**
（`test_settings.cc`，防止以后有人往复位里加一行把用户模板清掉）。

实现要点：`main/network_reset.cc::ResetNetworkConfigToDefault()` = Settings 清理 +
`SetApSsid("")` + `SetApPassword("")` + `UseDhcp()` + `ForgetSta()`；
**按钮与串口 `wifi resetnet` 走同一个函数**（因此"按钮会执行的代码"能在真机用串口验证）。
按钮回调在 esp_timer 上下文 → 经 `Schedule()` 投主线程（禁止在回调里写 NVS/操作 WiFi）。

## 3. ⚠ 一次"假事故"：我把自己的验证步骤误判成了神秘触发（**已更正**）

**经过**：烧入带复位按钮的固件后，我的验证脚本第 ③ 步**主动执行了 `wifi resetnet`**（验证功能，
日志里明确有 `NetReset: === 恢复网络默认配置 ===`），于是"AP名/密码/已保存网络/IP 模式"按设计被清空 ——
**这是预期行为，不是故障**。但随后第 ⑦ 步用串口逐个 `wifi set` 恢复时，
`wifi set ZTE_C97FF0` 撞上 `ESP_ERR_WIFI_STATE`（前一条 `wifi set 603sys` 正在连接中），
**恢复失败**，设备被我留在"STA 断开 + 驱动卡住（扫描返回 0 个 AP）"的状态。
更后面那个脚本的"复位前快照超时"其实是**设备已被我搞离线**，
我却**误读为"配置在我快照之前就被神秘清空"**，于是一路追查一个并不存在的触发源。

**更正后的结论**：**没有神秘触发**。证据链：
| 证据 | 结果 |
|---|---|
| 开机后 10 秒 GPIO5 电平序列（每 200 ms 采样，临时补丁） | **50 个点全为 1** —— 上电期间从未被拉低 |
| 6 次硬复位 + 多次烧录后的复位计数 | **始终 0**，无 `按下/松开/长按` 日志 |
| `rstmon 180` 空闲监视 | 变化 0 次、下降沿 0 次 |
| 代码路径穷举 | 清空 `st_ip/st_mask/st_gw` 的**唯一**写入点是 `Settings::ResetNetworkConfig()`，其运行时调用点只有按钮与串口 `wifi resetnet`；串口那条正是我自己下的 |
| 测试宿主隔离 | 测试哨兵只出现在测试 NVS(0xC00000)，主 NVS(0x9000) 无 —— 隔离有效 |

**真正的问题（值得记）**：复位后用串口连续 `wifi set` 恢复网络会撞 `ESP_ERR_WIFI_STATE`，
并可能让 STA 驱动进入"扫描返回 0 个 AP / `reason=201 NO_AP_FOUND`"的瞬态，**重启即恢复**
（真实用户不会走这条路：他们在页面上重新填 SSID/密码，或点「重新连接」）。

**凭据恢复能力仍被这次经历验证**：NVS 是日志结构，字段被覆盖前的旧条目仍在 ——
`esptool read_flash 0x9000 0x4000` 读出来即捞回两台网络的 SSID 与明文密码（**密码不写入仓库**，方法本身可复用）
（恢复时**低优先网络先 set**，保持原优先级顺序）。这条已写进 AGENTS。

**保留的加固措施**（本次为排查而加，都是长期有价值的）：
1. **开机 30 秒守卫**（上电电平不稳不会被判为长按）；
2. **按下/松开/长按全打日志**（含开机毫秒数）；
3. **持久化复位证据**（`net_rst_cnt`/`net_rst_epoch`，WiFi 页显示"曾被恢复默认 N 次 + 最近时间"）；
4. **`rstmon [秒]`** 引脚监视 + **`rstbtn`** 自检 —— 以后再遇到类似现象，5 分钟即可定性。

## 3b. 顺带修掉的真 bug

- 页面「清除所有已保存 WiFi」发**空 body**，而 `DELETE /api/wifi` 是 fail-safe（要 `index` 或 `all:true`）
  → 一直 400、按钮等于没作用。已改为发 `{"all":true}`。
- 用户此前在页面**改过 AP 密码**（NVS 里读到自定义值）→ 被这次**我的复位验证**清回默认
  `12345678`（说明 AP 密码功能在真机上确实好用）。

## 4. 另一个真 bug（我先前引入）：扫描结果被事件处理器抢走

- **现象**：串口 `wifi scan`（同步扫描）永远"找到 0 个网络"，而旧版本正常。
- **根因**：WiFi-artnet 工作时新增的 `WIFI_EVENT_SCAN_DONE` 处理器**无条件**
  `esp_wifi_scan_get_ap_records()`；同步 `Scan()` 也会收到该事件 → 事件任务先把结果取走，
  同步路径再取就只有 0 个（`esp_wifi_scan_start(blocking=true)` 与事件任务是竞态）。
- **修法**：新增 `s_scan_async_pending` 标志，**只有我们自己发起的异步扫描**才在事件里取结果；
  同步扫描时事件处理器只复位状态、不碰结果。
- **验证**：断开态下 `wifi scan` → **8 个网络**（含 ZTE_C97FF0）、`wifi ascan` → **10 个网络**。

## 5. 另一处真机观察：复位后 STA 可能进入"扫不到任何 AP"的瞬态

复位后我用串口连续 `wifi set`（两次）+ 大量扫描，驱动一度返回 `reason=201 (NO_AP_FOUND)`
且**扫描结果为 0**；`ESP_ERR_WIFI_STATE` 也出现过。**重启设备即恢复**（自动连回原网络）。
→ 记录为已知瞬态：复位/频繁改网络后用一次重启兜底，不要据此怀疑硬件。

## 5b. 事故根因取证（用户确认"没按按钮"后继续深挖）

**NVS 取证**（`esptool read_flash 0x9000 0x4000` 解析条目）显示最新页里有一串**连续写入**：

```
#86 wifi_list=""  #88 wifi_ssid=""  #90 wifi_pass=""  #92 ap_pass=""
#94 st_ip=""      #96 st_mask=""    #98 st_gw=""        #100 last_known_ep
```

**这个组合是唯一指纹**：字段表 StrFields 顺序（`wifi_list→wifi_ssid→wifi_pass→ap_ssid(跳过,已是空)→ap_pass→st_ip→st_mask→st_gw`）
= **`Settings::ResetNetworkConfig()` + `SaveSync()`**。页面上任何按钮都做不出这个组合：
「清除所有已保存 WiFi」= `ForgetSta()` 只清 3 个 wifi 键；「复原默认密码」只清 `ap_pass`；
「默认(DHCP)」只清 `ip_mode`。

**逐项排除**：
| 候选 | 结论 |
|---|---|
| 测试宿主写坏真机配置 | **排除**：测试 NVS(0xC00000) 里能搜到测试哨兵（`SENTINEL-`/`哨兵店铺名`），**主 NVS(0x9000) 里一个都没有** → 隔离有效 |
| 我从串口执行 `wifi resetnet` | **排除**：本次会话从未下发该命令（脚本只用了 `appass/ip/dhcp/disc/on/scan/ascan/set/rstbtn/httptest`）|
| 页面误触 | **排除**：页面没有任何入口能一次清掉这 7 个字段 |
| GPIO5 被硬件自发拉低 | **未复现**：新增 `rstmon 180` 监视 180 秒（每 50 ms 采样）→ **变化 0 次、下降沿 0 次**，网络配置也未被再清 |
| 物理按压 | 用户确认**没有按** |

**结论**：复位确实执行了（NVS 铁证），而唯一可达路径是 **GPIO5 长按** 或串口命令（后者已排除）
→ 那一刻 **GPIO5 确实被拉低了 ≥5 秒**（当时的固件还没有开机守卫与按键日志，所以没有留下日志）。
最可能是**接线侧**（GPIO5 上已接按钮/杜邦线，偶发碰地）。

**因此本次加的排查手段（下次可直接定位）**：
1. **开机 30 秒守卫**（上电电平不稳不会被判为长按）；
2. **按下/松开/长按全打日志**（含开机毫秒数）→ 下次日志里能看到"何时按下、按了多久"；
3. **持久化复位证据**：`net_rst_cnt` / `net_rst_epoch` 写入 NVS，**WiFi 页显示"网络配置曾被恢复默认 N 次，最近一次 <时间>"**
   → 即使没人看串口，也能知道发生过、何时发生；
4. **`rstmon [秒]`** 引脚监视命令（现场直接看有没有人被拉低）。

**顺带修掉两个真 bug**：
- 页面「清除所有已保存 WiFi」发的是**空 body**，而 `DELETE /api/wifi` 是 fail-safe 的（要求 `index` 或 `all:true`）
  → 一直返回 400、按钮等于没作用。已改为发 `{"all":true}`。
- 用户在这次事故前**在页面上改过 AP 密码**（NVS 里读到自定义值，8 字节）→ 被复位清成默认 12345678
  （说明 AP 密码功能在真机上是好用的，只是被事故清掉了）。
