# 评审：抽奖按钮（GPIO8）低电平触发 + 去抖 + 1 秒限流

> 设计 `specs/2026-10-11-button-active-low-debounce.md`　|　计划 `plans/2026-10-11-button-active-low-debounce.md`
> 用户要求："GPIO8 抽奖按钮 确认也是低电平触发，并且加有抖动处理，一秒内只能触发一次"

## 现象 / 差距

| 项 | 改造前 |
|---|---|
| 触发电平 | `Button(BUTTON_MODULE_GPIO, 1)` = **高电平触发**（与用户实际接线不符，AGENTS 里也写错了） |
| 去抖 | **没有** —— `esp_button` 4.2.1 的 `button_config_t` 只有 `long_press_time`/`short_press_time`，无可配去抖 |
| 限流 | **没有** —— 抖动/连击会连续调用 `LotteryController::Trigger()`（仅靠状态白名单兜底） |

## 修法

1. **板级参数**（`boards/esp32s3_lucky/config.h`）：
   `BUTTON_MODULE_ACTIVE_LEVEL=0`（按下为低）· `DEBOUNCE_MS=30` · `COOLDOWN_MS=1000`，
   并加编译期断言（电平 ∈{0,1}、去抖 < 限流、限流固定 1000ms）。
2. **纯逻辑闸门 `ButtonGate`**（`main/button_gate.{h,cc}`）：去抖（"等安静"语义：抖动期间窗口顺延）
   + 限流（距上次**被接受**的触发 < 1s 则忽略）+ 统计（接受/去抖吞掉/限流忽略/上次触发时刻）。
   选纯类是为了能在**宿主单测**里锁死边界（真机上很难复现抖动串）。
3. **接线**（`application.cc`）：抽奖与"长按打自检页"**各用一个闸门实例**（互不饿死）；
   被拒时 `ESP_LOGD` 记原因；回调仍 `Schedule()` 投主线程。
4. **串口 `btbtn`**：打印 引脚 / 触发电平 / 去抖 / 限流 / **当前电平** / 闸门统计 / 上次触发起始
   —— 现场按一下就能确认电平与去抖是否生效，**不需要出票**。

## 真机确认（用户要求"确认"的那一项）

```
I (816) App: [6/7] 抽奖按钮就绪 (GPIO8, active_low/按下=0, 去抖 30 ms, 限流 1000 ms)
btbtn → 当前电平=1（未按下/上拉正常）
```
上拉输入空闲读到 **1** ⇒ 按下时被拉到 0 ⇒ **确认低电平触发** ✓（若接线其实是高电平触发，
空闲置位会是 0，这里会立刻暴露）。

## 过程中的两个自省（都记进 AGENTS）

1. **测试期望不能凭直觉写**：我先写的两条断言（"220ms 那次算限流"、"999 后 1000 必接受"）
   连续两次挂掉。把 `button_gate.cc` 单独用 g++ 在主机上跑出**真实轨迹**后才明白：
   - 去抖是"等安静"语义 → 220ms 距上次事件仅 20ms，仍属抖动；
   - 999ms 被限流拒绝**也是事件** → 顺延窗口，1000ms 距它仅 1ms，物理上就是同一次抖动的尾巴，应当吞掉。
   于是按实测轨迹重写断言，并补了"限流拒绝后 1ms 再按"的专门用例固化该语义。
2. **ESP-IDF v6.1 的 `EXPECT_EQ` 消息参数是反的**（本项目 `LuckyExpectEq(a,b)` 内部按 `(b,a)` 调用
   Unity）→ 报错文本 "Expected X Was Y" 里的 X 是**实际值**。排障时别被这行字带偏。
